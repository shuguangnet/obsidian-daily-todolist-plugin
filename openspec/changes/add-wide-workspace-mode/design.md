## Context

当前 Vault Atlas HQ 默认以右侧叶子视图打开，这种窄栏模式适合快速查看和轻量操作，但对于首页统计、甘特图、AI Command Panel 和多卡片布局来说，可用空间明显不足。随着插件从“日常小工具”演进为“工作台”，需要一个能够在主工作区或宽叶子中使用的模式，同时保留现有窄栏入口。

当前约束包括：
- 现有视图类型只有一个，打开逻辑主要偏向 `getRightLeaf(false)`。
- 样式系统以侧栏密度优先构建，直接拉宽会出现留白、信息层级失衡或布局松散问题。
- 不能破坏原有右侧侧栏工作流；宽工作区模式应该是增强入口，而不是替代入口。
- 不在本次范围内控制整个 Obsidian UI 的“全屏”，只关注插件自身在更大工作区中的展示和打开方式。

## Goals / Non-Goals

**Goals:**
- 允许 Vault Atlas HQ 以宽工作区模式打开，使用户能在主编辑区或更宽叶子中使用插件。
- 为宽工作区下的核心页面提供专门布局适配，至少覆盖 Home、Stats、Gantt、AI Command Panel。
- 保留现有侧栏模式，并提供用户可理解的打开方式（命令、按钮或设置）。
- 建立页面宽度感知的样式分层，而不是简单把窄栏拉宽。

**Non-Goals:**
- 不实现真正浏览器式全屏。
- 不自动隐藏 Obsidian 左右侧栏、标题栏或其他全局 UI。
- 不在本次变更中实现演示模式或 kiosk 模式。
- 不重写所有页面的视觉设计，只优先解决宽工作区下的信息编排问题。

## Decisions

### 1. 采用“同一视图类型 + 不同打开策略”而非新增第二种 view type
宽工作区模式优先通过新的打开命令或打开策略，将现有 `DAILY_TODOLIST_VIEW_TYPE` 放入主区域叶子，而不是复制一套独立 view type。

备选方案：
- 新建 `wide-view` 类型：隔离更彻底，但会引入状态同步和双视图维护成本。

### 2. 用容器宽度驱动布局，而非用 tab 特判布局
宽工作区适配应由根容器 class 或宽度断点驱动，使 Home、Stats、Gantt、AI Command Panel 在大空间中自然重排，而不是在各 tab 中写大量 if/else 特判。

备选方案：
- 每个 tab 单独维护两套 DOM 结构：灵活但重复度高，维护成本大。

### 3. 窄栏与宽工作区共存
默认行为可继续保留右侧栏打开；新增明确的“在主区域打开”命令，用户自行选择工作模式。

备选方案：
- 全量迁移到宽工作区：会破坏已有使用习惯，也不适合快速查看场景。

### 4. 优先优化高收益页面
宽工作区首批重点页面：
- Home：多列卡片与更稳定的信息层级
- Stats：图表与指标栏展开
- Gantt：获得更长时间轴宽度
- AI Command Panel：输出区与输入区获得更舒适空间

其余页面可以先依赖响应式自然拉伸，再逐步增强。

## Risks / Trade-offs

- [宽工作区模式和侧栏模式共享同一 DOM 结构，容易相互牵制] → 使用清晰的根容器 class 和样式断点，减少局部 hack。
- [主区域打开后用户可能同时保留侧栏实例，造成多视图并存] → 明确命令语义，必要时在打开策略中优先复用已有实例。
- [甘特图和 AI 面板宽屏体验提升明显，但 Today / Memo 页提升有限] → 首版优先优化高价值页面，不追求所有 tab 一次做到位。
- [宽工作区模式会暴露现有间距与卡片栅格设计不足] → 接受首版会带动一轮样式整理，把它当成布局升级契机。
