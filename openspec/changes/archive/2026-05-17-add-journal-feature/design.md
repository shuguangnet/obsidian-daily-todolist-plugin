## Context

当前插件以 Daily Note 作为唯一数据源，已经在指定标题区块内管理 TodoList 和 Memo，并通过侧边栏视图展示首页、今日、备忘录、日历、甘特图和统计。现有 Memo 适合短文本碎片记录，但缺少一个能承载完整当日记录的 Journal 层，因此需要在不引入新存储和不接管整篇 Daily Note 的前提下，为 Daily Note 增加一个新的区块型能力。

约束包括：
- 继续以 Daily Note Markdown 为唯一事实来源。
- 继续遵循“只修改目标标题区块”的写入原则，避免改写整篇笔记。
- 保持 Obsidian 原生 DOM UI 实现，不引入新前端框架或外部依赖。
- 尽量复用现有 Todo/Memo 的解析与路径解析方式，减少新概念。

## Goals / Non-Goals

**Goals:**
- 新增 Journal 区块读写能力，支持获取今日日记内容与覆盖保存。
- 在侧边栏中提供独立 Journal 页签，给用户清晰区分 Todo、Memo 和 Journal。
- 在设置中允许配置 Journal 标题名，与现有 TodoList / Memo 保持一致的使用方式。
- 在首页或统计页提供 Journal 活跃度的基础概览，形成最小闭环。

**Non-Goals:**
- 不管理整篇 Daily Note 主体内容。
- 不引入富文本编辑器、Markdown AST 或所见即所得编辑体验。
- 不在第一版实现多模板、streak、关键词分析或跨日回顾系统。
- 不新增独立数据库、缓存文件或 Vault 外部状态。

## Decisions

### 1. Journal 采用“标题区块 + 整段正文”模型
Journal 将与 TodoList、Memo 一样锚定在 Daily Note 的指定标题下，但内容不是列表项，而是该标题到下一个同级标题之间的整段正文。这样可以在不接管整篇笔记的前提下，为用户保留较自由的日记书写空间。

备选方案：
- 管理整篇 Daily Note：自由度更高，但会与用户已有模板和其他区块发生冲突，写入边界不安全。
- 把 Journal 设计成带时间戳的列表流：实现更轻，但会与 Memo 语义重叠。

### 2. Journal UI 采用独立 tab，而不是塞入 Today 视图
在现有架构中，Today 已聚焦任务录入与任务列表。Journal 作为不同心智模型的数据类型，使用独立 tab 可以降低混杂感，也便于后续扩展模板、最近回顾等能力。

备选方案：
- 合并到 Today：入口更集中，但页面会变得过重，Todo 与长文本日记的交互节奏不同。

### 3. Journal 读写抽象为独立模块
将新增一个与 `memos.ts` / `markdown-tasks.ts` 同层的模块，负责：
- 读取指定标题区块正文
- 在标题不存在时自动补齐标题
- 覆盖保存区块内容
- 判断区块是否为空

这样可将解析/写入细节从 `view.ts` 中抽离，保持视图层只关心展示与交互。

### 4. 活跃度统计先做最小集合
第一版不做复杂 journal analytics，只提供最小可见价值：
- 当前月份有日记的天数
- 今日是否已有日记
- 最近若干天可选摘要展示（若实现成本可控）

备选方案：
- 一开始就做 streak、字数统计、情绪标签等：价值更高，但会显著扩大数据模型和 UI 范围。

## Risks / Trade-offs

- [Journal 区块内容为自由文本，解析边界比 Memo 更敏感] → 通过“标题到下一个同级标题”作为唯一边界，避免正文内做细粒度结构解析。
- [覆盖保存可能误伤用户并发编辑] → 第一版遵循当前插件的简单模型；如发现内容已变化，可在保存前重新读取并以当前编辑值整体覆盖该区块。
- [新增 tab 会让导航继续膨胀] → 保持 Journal 页签功能单一，避免在首版塞入过多二级能力。
- [首页/统计加入 Journal 可能增加跨日期读取成本] → 复用现有按月范围读取逻辑，只统计当月存在的 Daily Note。
